# Target-program coverage: `zip-fuzzer` → Info-ZIP UnZip 6.0 (worked run)

Concrete, reproducible execution of the "target-program coverage" recipe from
[code_coverage_of_generated_outputs.md](code_coverage_of_generated_outputs.md)
(§4), the methodology the FormatFuzzer paper actually uses (LCOV line
coverage of a real consumer, not this repo's own validity-% metric). Run on
2026-08-10, macOS (Darwin), Apple clang.

## Result

**26.0% line coverage (1,380 / 5,304 lines), 50.4% function coverage
(60 / 119)** of Info-ZIP UnZip 6.0's `unzip` binary, from 2,000 files
generated by `zip-fuzzer` and checked with the same `unzip -t` invocation
[checkers/zip.sh](../checkers/zip.sh) uses. 1,412/2,000 (70.6%) of the
generated files passed that check (exit code 0 or 1, per `checkers/zip.sh`'s
own definition of "valid") — this is the separate validity metric, included
here only to show it's not the same number as coverage.

## Findings worth acting on

- **`inflate.c` (DEFLATE decoder) at 0.7% and `explode.c` (IMPLODE method) at
  0%**: the generated corpus is almost entirely **stored** (uncompressed)
  entries — a spot-check confirmed a generated file was `compression
  method=store`. `zip.bt`/`zip-fuzzer` isn't exercising the deflate or
  implode compression codepaths at all. This is the single biggest lever to
  raise this number, and it's exactly the kind of gap the paper's own Table
  4/6 ZIP coverage result implicitly depends on getting right — if the
  generator doesn't vary the compression-method field, the corresponding
  decoder code can never be covered no matter how many files you throw at
  it.
- **`zipinfo.c`/`list.c` at 0%** is a driver artifact, not a template gap:
  `unzip -t` never touches the `-Z`/`-l` listing codepaths. Don't "fix" the
  template for this — if listing coverage matters, add `unzip -l`/`-Z` runs
  to the driver loop instead.
- **`funzip`/`unzipsfx` object variants (trailing-underscore `.o` files) show
  no coverage** because only the `unzip` binary was exercised — expected,
  not a bug. `unshrink.c`/`crypt.c` scoring reasonably well (57%/70%) shows
  the corpus *does* vary at least the shrink method and encryption, just not
  deflate/implode.

## Reproduce it

```bash
# 1. Build UnZip 6.0 with gcov instrumentation (bypass the `macosx` make
#    target, which hardcodes -O3 and no --coverage; drive the underlying
#    `unzips` target directly instead)
curl -L -o unzip60.tar.gz https://downloads.sourceforge.net/infozip/unzip60.tar.gz
tar xzf unzip60.tar.gz && cd unzip60
make -f unix/Makefile unzips \
     CFLAGS="-O0 -g --coverage -Wall -DBSD" \
     LF2="--coverage"
cd ..

# 2. Generate a corpus with this repo's fuzzer (run from the FormatFuzzer repo root)
mkdir -p zip_corpus
./zip-fuzzer fuzz $(for i in $(seq 1 2000); do echo zip_corpus/f$i.zip; done)

# 3. Drive the instrumented binary with the same command checkers/zip.sh uses
cd unzip60
for f in ../zip_corpus/*.zip; do
  yes | ./unzip -P '' -t "$f" >/dev/null 2>&1
done

# 4. Aggregate and report
lcov --capture --directory . --base-directory . --output-file ../zip_target.info
lcov --summary ../zip_target.info
genhtml ../zip_target.info --output-directory ../coverage_html_zip
open ../coverage_html_zip/index.html
```

## Environment notes (this machine)

- `lcov`/`genhtml` were **not installed** at the start of this session;
  installed via `brew install lcov` (now at `/opt/homebrew/bin/lcov`,
  version 2.5, using LLVM gcov emulating gcov 4.2.0 under the hood).
  `/usr/bin/gcov` (Xcode CLT) alone is not enough — `lcov` is what turns raw
  `.gcda` files into the `--summary`/HTML report.
- `downloads.sourceforge.net` was reachable from this sandbox without any
  proxy setup.
- The `macosx`/`macosx_gcc` targets in `unix/Makefile` hardcode
  `CFLAGS="-O3 -Wall -DBSD"` and `LF2=""` inside the recipe text (not via a
  variable that a command-line override can reach), so `make macosx
  CFLAGS=...` silently ignores your override. Driving the underlying
  `unzips` target directly, as above, is what actually lets `CFLAGS`/`LF2`
  take effect.
- All build/run artifacts from this session live under the session
  scratchpad (ephemeral, not part of the repo) — rerun the commands above
  (from the FormatFuzzer repo root, adjusting paths) to regenerate; nothing
  from this run was committed.

## Applying this to another format

Swap step 1's source tree and step 3's driver command for the target in
question — see the mapping table in
[code_coverage_of_generated_outputs.md §4](code_coverage_of_generated_outputs.md#applying-this-to-other-formats).
`jpg`→libjpeg-turbo (`djpeg`) or `gif`→gif2png are the next-cheapest to try;
`png`/`bmp` need a purpose-built test driver since `checkers/png.sh` and
`checkers/bmp.sh` shell out to ImageMagick rather than calling libpng/
gdk-pixbuf directly.
